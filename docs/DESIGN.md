# tui-world 设计文档

> v0.1 · 2026-10-11 · 状态：草案（两项已定）
> 已定：① 隐喻 = 世界是一扇窗、机器是窗框与仪表　② 前端 = 浏览器双栏
> 待定：③ M0 的体裁（场景模板）先做哪几个

## 0. 摘要

tui-world 是一台**对话驱动的世界显示器**：左侧是对话框，右侧是一个持续存在的地方，它因为这段对话而改变——改气氛、换焦点、添物件、发生事件。它不是"每轮生成一张图"，而是**一个地方在演变**；画面语言是字符网格（TUI），不是照片或视频。

技术上有三个关键：**世界状态机**（不是每轮重画）、**声明式工具表**（LLM 做选择，系统做几何）、**量化风格化着色器**（把任何素材压进同一套 TUI 美学）。

## 1. 产品定义

### 1.1 一句话

左边聊天，右边是一个正在发生的地方。

### 1.2 验收标准（可检验）

1. 聊《哈利波特》40 轮，右侧始终能看出是"同一个地方"在演变，期间出现过城堡、也出现过额头上那道疤——**相关，但不固定**。
2. 任何一轮发言后，右侧 **300 ms 内**有可见反应；慢素材到达前用"字符落定"遮罩，不出现白屏。
3. 十分钟不操作，画面仍在缓慢呼吸（有生命感），CPU 占用可忽略。
4. 画面出问题时，仪表层（延迟、token、工具日志）永远真实——"显示器没坏"。

### 1.3 非目标

- 不做文生图工具：不追求每轮产出高清插画。
- 不做视频生成：右侧没有真实人物，不做 AI 短剧。
- 不做聊天皮肤：右侧不是装饰，它是有状态、可回溯的。

## 2. 总体架构

### 2.1 四层 + 两条贯穿线

```text
        用户输入
           │
   ┌───────▼────────┐   对话历史 + 世界摘要
   │ Director (LLM) │──────────────────┐
   └───────┬────────┘                  │
           │ 工具调用（声明式，无坐标） │ 反馈回路
           ▼                           │
   ┌────────────────┐                  │
   │  World State   │◄─────────────────┘
   │  （唯一事实）  │
   └───────┬────────┘
           │ 增量 patch
           ▼
   ┌────────────────┐   ┌────────────────┐
   │  Concretizer   │◄──│ 素材/模板/检索 │（慢路径：秒级）
   │  概念 → 元素   │   │ /生成（可选）  │
   └───────┬────────┘   └────────────────┘
           ▼
   ┌────────────────┐
   │   Stylizer     │  任意素材 → 字符网格（char/fg/bg）
   └───────┬────────┘
           ▼
   ┌────────────────┐
   │   Presenter    │  脏矩形 + 动效时钟 + 转场 + 后处理
   └───────┬────────┘
           ▼
        右侧画布
```

| 层 | 职责 | 明确不做 |
|---|---|---|
| Director（LLM） | 把对话归约成"世界状态变更"：选择、节奏、情绪 | 不写坐标、不碰像素 |
| Concretizer | 把概念落成画面元素：模板 / 程序化 / 检索 / 生成 | 不管最终长什么样 |
| Stylizer | 把任意来源压进 TUI 美学：字符网格、字形、调色板 | 不解释语义 |
| Presenter | 合成、动效、转场、推帧 | 不改世界状态 |

贯穿线一：**World State** —— 唯一事实来源，可序列化、可回放、可 diff。
贯穿线二：**反馈回路** —— 渲染后的信号（可读性告警、帧率）回喂 Director。

### 2.2 一轮对话的时序预算

| 时刻 | 发生什么 | 谁做的 |
|---|---|---|
| t+0 | 用户消息进左侧对话流 | 前端 |
| t<300 ms | 世界给出"已收到"的反应：一次呼吸/脉冲/解码闪烁 | 本地，不等模型 |
| t+0.8~3 s | Director 返回工具调用（世界 patch） | LLM |
| +50 ms | patch 应用，元素生成（模板/程序化，本地） | Concretizer |
| +100 ms | 新帧只重绘变化区域 | Stylizer + Presenter |
| +300 ms | 落定动画结束，世界进入新状态 | Presenter |
| 3~30 s | （慢路径，可选）生成/检索素材到达 → 用转场切入替换占位 | 异步 |

**核心原则：世界永远不等模型。** 模型思考时，世界在呼吸。

## 3. 核心机制

### 3.1 世界状态 WorldState

```python
WorldState:
    seed: int                      # 世界随机种子（可复现）
    place: {kind, params, bg}      # 地方：hall / room / city / void / page ...
    mood:  {palette, energy, brightness, weather}
    focus: {concept, camera:{zoom, pan, tilt}}
    props:   [{id, kind, params, at, born, ttl?}]
    actors:  [{id, kind, params, at, mood}]
    events:  [{at, type, payload}]         # 已发生：雷击、开门、翻页
    chronicle: [{turn, summary, patch}]    # 变更日志：可回放、可"回忆"
```

规则：**每轮只允许增量 patch**。任何"重画"都必须显式写成 `place(...)`（换地方），并在 chronicle 留痕。这是"同一个地方"成立的唯一办法。

### 3.2 工具表（声明式状态变更）

```json
{"tool":"set_mood","args":{"palette":"amber","energy":0.7,"weather":"fog"},"reason":"谈话变沉重"}
{"tool":"focus","args":{"concept":"哈利·波特额头上的那道疤","camera":{"zoom":3.0}},"reason":"他摸了摸额头"}
{"tool":"place","args":{"kind":"tower","params":{"height":9,"style":"gothic"},"at":"north"}}
{"tool":"spawn","args":{"kind":"wand","at":"near:harry"}}
{"tool":"spawn_image","args":{"prompt":"...","use":"prop:portrait"}}
{"tool":"emit_log","args":{"text":"SYS channel open"}}
{"tool":"beat","args":{"intensity":0.9}}
```

约束：

- 工具表里**没有绝对坐标**。`at` 只能是空间关系：north / behind / near:\<id\> / focus / offstage。
- 每个调用带 `reason`，它会作为"系统日志"出现在仪表层——既给用户看，也是模型自己的记忆锚点。
- schema 校验 + 一次自动修复重试；仍失败 → 降级为 no-op 并 emit_log。**世界不能崩**。

### 3.3 双路径延迟与"思考中呼吸"

- **快路径**（本地，<100 ms）：体裁模板 + 程序化元素。必须保证"任何主题都至少有合理画面"——靠通用体裁兜底（星空、房间、城市、走廊、书页、光斑）。
- **慢路径**（秒级）：检索素材 / 生成模型。到达后用转场（carrier）替换占位元素。
- 心理事实：用户能容忍 3 秒等待，只要这 3 秒里画面在动、且动得"有意义"。

### 3.4 仪表层（与画面共位）

永远真实：模型名、延迟、token 数、工具日志、世界版本、帧率、seed。它同时是"这台机器在思考"的在场证明，也承担转场遮罩：模型卡住时，仪表层在跑。

### 3.5 反馈回路（可读性守卫）

渲染完成后跑一次可读性评估（我们已有的 `eres` 信号：局部残差能量 ÷ 原能量）：

- 某块信息密度超过格子能表达的极限 → 自动 `focus(camera.zoom × k)`，或换成更空旷的构图。
- 把"世界摘要 + 上一帧告警块的位置"作为 system 上下文回喂 Director，让它知道画面上正在发生什么、哪里看不清。

## 4. 渲染管线（Stylizer 细节）

### 4.1 三层字符关键帧

每个格子由三层叠加决定（来自已跑通的字符化实验）：

| 层 | 内容 | 说明 |
|---|---|---|
| `art` | 字形（斜杠、反斜杠、竖线、短横、冒号等） | 用结构张量取局部边缘方向来选字形 |
| `shade` | 亮度 0–7 | 决定字形密度与留白 |
| `part` | 分类色 d/s/g/b/l | 主色底衬 + 1px 缝隙，得到点阵质感 |

**已实测的边界**：自动 tracer 只能给出"色彩分类"，给不出"解剖部件"（头/发/手/裙）。没有解剖信息就做不了局部动作。因此现阶段定位：**角色不追求可动**，先做"无脸徽章 / 剪影 / 符牌"级别的人物——这恰好也是 TUI 美学的自然形态。

### 4.2 成本实测

| 项目 | 实测值 | 结论 |
|---|---|---|
| 96×64 网格，纯 Python + PIL 全帧渲染 | 165 ms/帧（48 帧 7.9 s） | 实时必须 numpy 化 + 脏矩形 |
| 单元格尺寸 | 5×10 px，输出 480×640 | 右侧面板约 700×500 px ⇒ 约 140×50 格 |
| 人脸在此网格下 | 一张脸约 7×8 格，一只眼约 2×1 格 | 一张脸 = 一个符号，不是肖像 |
| 可读性校准 | 合成图 0% 告警；边缘行者 25%；PV 预览 38%；PV 封面 42% | 是可靠的**相对**信号，不是精确仪器 |

### 4.3 信息密度上限与变焦（关键结论）

露西那张参考图里有 5 张脸、6 只眼挤在一块约 35×41 格的区域里——那块"没画好"不是算法问题，是**信息密度超限**。判定性实验：同一块内容**推近就成立**（`shard.duo.png` 里眼睛浮现出来了）。

⇒ **产品必须提供景别（变焦）能力**，并在信息超限时自动推近。这是产品能力，不是渲染能力。

### 4.4 转场

复用引擎的 carrier 思路：**有东西可见地穿过切点，并"造成"了下一幅画面**（一片字符、一道光、一次翻页）。世界切换（`place`）不突兀的关键在这里，不要用淡入淡出。

### 4.5 体裁库（三档，按成本排序）

| 档 | 手段 | 延迟 | 覆盖 |
|---|---|---|---|
| 1 | 模板 + 程序化（本地） | <100 ms | 场所、天气、光效、几何体——永远可用 |
| 2 | 检索素材 → Stylizer 量化 | 0.3–3 s | 具体物件（城堡照片、道具、徽记） |
| 3 | 生成模型（可选） | 3–30 s | 找不到的、专属于用户的画面 |

优先级：1 永远在跑 → 2 到了就替换 → 3 到了再替换。**任何时刻画面都是完整的。**

M0 起步用的 4 个通用体裁（选"哪里都能落"的，先跑通链路）：

| 体裁 | 画面 | 覆盖的话题 |
|---|---|---|
| `void` 星空 | 深空星野，偶尔有东西划过 | 抽象、情绪、宇宙、生死 |
| `room` 室内 | 桌面、窗、台灯、窗外天际线 | 日常、工作、私人谈话 |
| `city` 城市 | 建筑天际线、塔、雨、霓虹 | 故事、冒险、赛博、社会 |
| `hall` 大厅 | 哥特拱、柱廊、烛火、长桌 | 奇幻、史诗、哈利波特这类 |

## 5. 与已 fork 引擎（tuikit）的关系

### 5.1 复用表

| tuikit 模块 | 用途 | 备注 |
|---|---|---|
| `space.py` | 3D 线框 + 相机 + 隐藏线消隐 | 场景几何主力 |
| `glyph.py` | decode 打字、token chip、TUI 盒子、文字精灵 | "字符落定"遮罩、精灵 |
| `carriers.py` | 转场载体 | 世界切换的关键 |
| `chrome.py` | 页眉/页脚/字带 | 仪表层骨架 |
| `post.py` | bloom / 扫描线（numpy） | 风格统一 |
| `wave.py` | 波形 | 用声音驱动世界能量（可选） |
| `ease.py` | 缓动 | 直接可用 |
| `film.py` / `timing.py` / `project.py` | 时间线 / 节拍 / 工程加载 | 需要改造，见 5.2 |
| `render.py` | 离线渲染 CLI（stills/render/strips） | 保留：导出与回放 |

### 5.2 必须改造的点

tuikit 的原语是 `frame = f(t)`：离线、纯函数、24 fps、全帧重绘、进程池并行、面向 1280×720。实时系统要求 `frame = f(state, t)`：

1. `Clock` 从"歌曲时间"换成"墙钟 + 事件时间"（无歌模式，timing 依赖可缺省）。
2. 全帧重绘 → **脏矩形**：每个元素记录包围盒，只重绘变化区。
3. 进程池并行 → 单进程 + 帧队列（并行只留给导出/回放）。
4. `PROJECT.yaml` 的 song / timing 字段变成可选。

## 6. 工程结构与选型

### 6.1 目录（拟）

```text
tui-world/
  runtime/tuikit/        # 引擎（已 fork、已解耦）
  core/
    world.py             # WorldState + patch + 序列化
    director.py          # LLM 接口：对话 → tool calls
    tools.py             # 工具表 schema + 校验 + 修复重试
    concretize/          # 概念 → 元素：模板、程序化、检索
    stylize/             # 元素 → 字符网格（吸收 lab 的实验成果）
    present.py           # 合成、脏矩形、动效时钟、推帧
  server/                # 本地 HTTP / WebSocket
  ui/                    # 左对话 + 右画布
  docs/
```

先做成一条可跑的 CLI（`probe`），前端放最后——因为未知不在前端。

### 6.2 帧传输：字符缓冲，不是图片

每帧 = `{cols, rows, cells:[{ch, fg, bg}]}`。140×50 = 7000 格，未压缩约 49 KB，差分后通常 <2 KB。前端 canvas 用等宽字体绘制；扫描线 / 辉光 / 暗角这类**像素后处理放前端 GPU** 最便宜。
（M0 简化：服务端直接出 PNG；M1 再切字符缓冲。）

前端形态**已定（2026-10-11）：浏览器双栏**。

### 6.3 依赖

Python + Pillow + numpy + PyYAML（引擎既有）；LLM 任意支持 tool calling 即可，接口层做成可替换。

## 7. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M0 竖直切片** | 一句中文 → Director → 世界 patch → 一帧 PNG。先做 3–5 个体裁模板（星空 / 房间 / 城市 / 大厅 / 书页），只实现 `set_mood` / `focus` / `place` / `emit_log` | 改一句话，画面合理地变；可读性无告警 |
| **M1 实时世界** | WorldState + patch + 脏矩形 + 落定动效 + 浏览器双栏 + 仪表层 + 左对话框 | 连续 20 轮是同一个地方在演变；≥10 fps；<300 ms 反应 |
| **M2 相关但不固定** | 概念具体化（多候选）+ 变焦守卫 + 检索素材风格化 | 哈利波特场景里，城堡 / 伤疤 / 魔杖至少出现两种；超限块自动推近 |
| **M3 慢路径与记忆** | 生成式素材接入 + 反馈回路回喂 + chronicle 回放 | 断线重开，世界能按 chronicle 恢复到之前的样子 |

## 8. 从哪里开始（结论）

**先做 M0 的竖直切片：`concept → 体裁 → 一帧`，不碰前端、不接除 LLM 以外的任何服务。**

理由：这个产品最大的未知不是渲染——渲染我们已经有引擎、有实测数据、有明确的改造清单。真正的未知是 **"LLM 能不能当好这个导演"**：它会不会把"聊聊哈利波特"落成一组合理的世界指令（改气氛、聚焦那道疤、在天上放一只猫头鹰），还是只会吐出泛泛的形容词。这个未知必须用最小成本先证伪：一个 CLI，输入一句话，输出 tool calls + 一张 PNG。

## 9. 风险与未决项

- ~~显示器的隐喻~~ → **已定（2026-10-11）：世界 = 一扇窗，机器 = 窗框与仪表。**
  推论：窗外是无限世界（城堡、星空、城市都装得下）；"机器内部"的视觉只出现在窗框与仪表上（扫描线、日志、token、延迟）。窗框承担风格统一，也是"显示器没坏"的证明。
- LLM 工具调用的稳定性：schema 校验 + 修复重试 + 降级 no-op（世界不能崩）。
- 成本与速度：每轮一次 tool-calling；慢路径要能取消、能被更新的意图覆盖。
- 素材许可：不引入上游 CC BY-NC-SA 美术（本次清理已移除）。
- 信息密度上限：已实测，靠变焦解决；必要时换景别，而不是换算法。

## 11. M1 实装与首轮反馈修正（2026-10-11 下午）

首轮实测后用户提了三条，逐条落到代码：

### 11.1 "画面太抽象、认不出来" → 主因是取景，不是画法

- **取景拉近**：wide 26 → 16，mid 13.5 → 11.5；全景且没有 focus 时，相机对准
  最近 6 件物品的质心（`_camera` 的质心兜底）。实测冰川从 ~70 px 长到 ~110 px，
  线的可辨识度立刻上来。**同一形状，只是站远了就看不清**——这条以后调画面前先查取景。
- **新增画法**：`_h_glacier`（山脊折线 + 雪线横纹）、`_h_tree`（树干 + 三层树冠）、
  `_h_figure`（头 + 躯干 + 手臂）、`_h_breath`（侧脸 + 向右散开的弧）。
  kind 用别名表注册（`_reg`），未注册的 kind 落到 `_h_marker`。
- **兜底不再装成方块**：`_h_marker` 改成"框 + 问号"，承认这一块画不出来，
  比糊一个形状更诚实，也能提示用户换个词。
- **深度陷阱（踩过）**：画在物体**远侧**（z 偏移为正）的内部纹理会被深度缓冲吃掉，
  出现"破洞"；把横纹放到近侧（`z - 0.42`）即干净。见 `lab/glacier_lab.py` 的对照实验。
- **世界内标签只能 ASCII**：consola.ttf 没有中文字形，`v.label` 画中文会静默变空白；
  中文只出现在窗框与日志带（那里用 PIL 字体，有 CJK 变体）。

### 11.2 "不要以展示图像为终极意义" → 提示词改成"聊天顺便"

`director.SYSTEM` 重写：定位是"一个正在聊天的人，身边有块像窗户的显示器"；
**大多数回合 0 个工具调用，一次最多 3 个**；宁可不动，不要为了动而动。
实测（`lab/talk.py`）四轮：闲聊 1 个（调灯）、聊到冰川 3 个、聊到喘不上气 2 个、

## 12. 素材路线接回（2026-10-11 晚）：参考图 → 字符画

用户看过纯程序化画法的结果（"太原汾河" = 7 条横线）后明确要求走回参考图那条路线。
两条路线的差别是**信息**：

| 路线 | 输入 | 带的信息 | 适合 |
|---|---|---|---|
| 程序化 `place` | 一个词 | 无，只有几何模板 | 形体简单的东西（城堡、树、冰川） |
| 素材 `show` | 一张参考图 | 轮廓、明暗、内部结构 | 角色、真实场面、地标 |

### 12.1 管线

1. **离线**：`python tools/trace.py asset <参考图> assets/<id> --name 大卫 --alias david,露西,…`
   → `<id>/key.json`（art / shade / part 三层字符网格，96×64 格）+ 预览图 + 原图副本。
2. **运行时**：`core/assets.py` 按**素材自带色板**重新上色（色相是内容的一部分——
   皮肤/衣服/环境要分得开，只往当前世界墨色偏 12%），加浮现（1.25 s）／摇曳
   （脖子以下正弦位移，头再多偏一点）／偶发闪烁，然后等比居中贴进画布
   （后景压暗 75%，一圈窗边）。
3. **模型侧**：新工具 `show(asset)` / `hide()`；`Director` 启动时把素材清单
   （id / 中文名 / 别名）写进系统提示，并说明"素材库以外的一律用 place"。

### 12.2 实测

- 整帧渲染：带信号 65 ms，普通世界 33 ms；动画循环 ~8 fps（`Session._animate`），
  **只在有信号时跑**，其余时间完全不动。
- 前端：`/state` 里 `anim=true` 时轮询间隔 900 ms → 130 ms，且每轮都刷帧。
- 实测对话"说到大卫和露西，我最想看的还是那一张" → 模型自己调了 `show(david)` +
  `set_mood`，没有硬画；连续两帧内容不同（动效在跑）。

### 12.3 还没有的

- 素材库目前只有 `david` 一张。缺"场景/照片"类素材（例如一张汾河的照片）——
  有图就能加，流程是同一条命令。
- 预烘焙的完整动作序列（`pose` / `materialise` 的逐帧烘焙）还没做；现在是实时算的轻动效。

## 13. 素材质量：参数比算法重要（2026-10-11 夜）

用户看过"程序化画法"的成品（"晋阳湖"= 7 条横线）后说太烂太抽象，并转述了原作者的判断：
「做几个预制的 TUI 动画放进去，再按需要微调」；以及更激进的版本「爬大量参考图 →
自动形成资源库 → 预制与微调全自动 → 再挂一个大模型」。

我的结论：**方向对，但"全自动"是幻觉——好看来自"挑 + 调"，而挑和调必须有人在环。**

### 13.1 三个参数实验（`lab/candidates.py`）

同一张参考图、同一套描图代码，只换参数，质量差一个档次：

| 参数 | 效果 |
|---|---|
| 网格密度 96×64 → 120×80 | 脸部从"能认出"变成"看得清眼睛"，key.json 仍只 39 KB |
| 裁切（全身 → 上半身） | 主体占比翻倍，细节立刻可用 |
| 反差 ×1.35 | 描出的暗部不再糊成一团 |

→ 所以微调不是"后期人工修图"，而应当是**软件的第一等公民**。

### 13.2 这一版实装的

- **密度**：david 素材重描为 120×80（`.venv\Scripts\python.exe tools\trace.py asset ...`）。
- **构图**：信号上屏从"等比缩在中间"改成"最多放大 1.5 倍、绝不超宽、往上偏一点截"，
  画面从"小人 + 大片空边"变成"顶格的脸 + 旁边的另一个角色"。
- **动效预烘焙**：摇曳/闪烁的 13 张帧按 (素材, 调色板) 烘焙一次，
  之后每帧只贴图——稳态整帧 85 ms（原先 150–500 ms），动画流畅度从 ~1.5 fps 提到 3–5 fps，
  且不再占着一整个核。踩过的坑：预烘焙的"闪帧"曾用 t=0.06 生成，被当成开场浮现期，
  只画了 5% 的格子（浮现进度与动画时间必须分开传参）。
- **近似替代**（提示词层）：聊到的东西不在素材库里、但库里有同类时，允许拿它当
  「近似的记忆」并说明是近似；没有相近的就别硬 show。

### 13.3 下一步（按收益排序）

| 优先级 | 事项 | 为什么 |
|---|---|---|
| P1 | **素材工作台**：拖图 → 6 个候选 → 滑杆微调（反差/密度/裁切/色板）→ 入库 + 自动打标签 | 这就是"预制过程自动化"的真正形态；把"挑和调"变成 10 秒的事 |
| P2 | **动作模板库**：呼吸 / 摇曳 / 入场浮现 / 故障 / 雨 / 推镜，参数化、可套用 | 现在是写死的一种摇曳；模板化之后素材数量才能规模化 |
| P3 | **近似替代 + 标签检索**（从提示词规则升级成真的检索） | 素材库不可能什么都有，命中率决定体验 |
| P4 | **半自动采集**：手动喂图 + 可描性评分（对比度/主体占比/背景干净度）自动劝退糊图 | 爬图解决不了版权，也解决不了"糊图描出来一定是垃圾" |

## 15. 动作模板库（2026-10-11 深夜）：一套模板套所有素材

素材与动作解耦：素材是"画了什么"，动作是"怎么上台"。`core/assets.py` 定义
`MOTIONS = sway / breathe / emerge / glitch / rain / push`，`Signal(asset, pen, motion)`
按名字分派；稳态帧仍走"12 帧预烘焙"，缓存键加了 motion，互不串帧。

| 动作 | 效果 | 稳态 |
| --- | --- | --- |
| sway（默认） | 轻微摇曳，每轮开头短闪 | 烘焙 12 帧 |
| breathe | 摆幅收小 + 亮度约 ±8% 的呼吸脉动 | 烘焙 12 帧 |
| emerge | 开场 1.6 s 自下而上逐格浮现 | 普通帧 |
| glitch | 1.15 s 周期，近半时间高强度字符乱闪 | 闪帧/普通帧交替 |
| rain | 像素级竖线雨幕覆盖（不占字符格） | 带雨帧 |
| push | 开场 1.05 s 从 1.18x 缓收到 1.0（以脸为中心） | 普通帧 |

接线：`show` 工具加 `motion` 参数（枚举 + 中文别名归一化：推近→push、下雨→rain、
故障→glitch……）；`world.signal_motion` 随 show 存储；SYSTEM 给出语义提示
（"想看清"→push、雨→rain、安静→breathe）。实测模型会自选：雨里的大卫 → rain，
安静的露西 → breathe，想看清纹路 → push。

## 16. 可描性回归修复与评分（2026-10-11 深夜）

露西素材入库后"像一坨色块"，定位出两个真 bug，顺带补齐评分入口：

1. **去背种子污染**（`_outside_mask`）：旧实现把"颜色接近任一粒边缘种子"的
   连通区都当背景；人物压在画框边上时（头发触到图片边缘）人体被整片当背景
   压黑，去背反相。改为：种子只取边缘**主导色簇**（4 档量化取最大桶），
   传播用相邻格颜色差 < 0.10（渐变背景整片吃掉、人物轮廓大反差自然停下）。
   露西 cover 47% → 73%，画面从抽象色块变成能认出"低头的少女"。
2. **冷调肤色缺失**（`tools/trace.py` 的 `classify`）：动漫常见的浅粉/暖白肤色
   （h>=0.78、s 0.09~0.24）原来落到蓝白 "l"。补一条 → "s"。露西脸上出现皮肤色，
   david 更饱满；黑白漫画 s≈0 不受影响。
3. **可描性评分**：新增 `sketch_score()` 与 `/wb/score` —— 分辨率 / 对比度 /
   主体占比 / 背景干净度加权 0~100 + 人话建议（"画面偏灰，反差可加大"）。
   选图后状态栏显示"可描性 XX"；漫画页缩略图右上角自动标分（4 并发懒加载），
   翻页时一眼挑好图。

另：素材库每条加「调」（回填画布，同 id 覆盖式重入库）/「删」入口；参数区加白话
说明行；候选自动选中 ★ 推荐项；选图后自动取景。

## 17. 自动取材与提示词主动性（2026-10-11 深夜·续）

"素材库不应该是它的全世界"——把取材变成导演可以自己走的第三条路：

1. **capture 工具**（`core/tools.py` + `core/director.py`）：聊到角色/名场面/地方，
   导演可以自己发起取材（query + motion + reason），先打一句招呼再调它。
   素材两条路固定为：库里有 → show；值得找、库里没有 → capture。（原来还有第三条
   place「让系统自己画」，2026-10-11 按用户要求砍掉，见 §20。）
2. **取材器**（`core/take.py`）：按序尝试本地 Pixiv 内容索引（58 张全量打标完成）
   → 漫画系列名匹配 → **网搜兜底**（`core/webfetch.py`：Bing 图搜走 socks 代理，
   curl.exe 免依赖；本机 http 代理对 bing 断、socks 通）。产出走工作台同管线。
3. **视觉挑选**（`core/vision.py:pick`）：网搜候选下载后，先让视觉模型挑"最适合描成
   两色字符画"的一张（主体单一 / 轮廓清楚 / 背景干净 / 少文字），失败回退可描性评分。
   实测把"哈利波特"从海报（文字糊成噪点）换成单主体人物图。注意推理型视觉模型
   max_tokens 要给足 2000，否则推理吃光 token、正文为空。
4. **异步上屏**（`core/app.py` `_capture`/`_capture_worker`）：库里已有 → 直接 show；
   没有 → 后台线程取材，描好自动上屏 + 追加系统消息（取材中不阻塞聊天）。
5. **提示词主动性**：SYSTEM 改为"世界显示器是你眼里的世界，聊到值得看一眼的东西
   顺手放上去，不用等用户点名；多数回合不碰屏幕"；capture 的 query 要写给图搜：
   越具体越好（「霍格沃茨城堡」优于「魔法世界」）。
6. **参数白话指南**：工作台参数区常驻一行白话（密度=网格粗细……），「每项怎么调？」
   展开 `#guide`：逐项含义 + 什么情况往哪边调 + 推荐流程。

## 18. 「再来一张」：取材去重与更严的选图（2026-10-11 深夜·续二）

症状：聊完初音、库里已有一张，再说"再来一张/看看别的"，系统永远把同一张推回来——
`_capture` 一见库里命中就短路，取材器也从不记录"这张参考图用过了"。

1. **来源指纹 src_fp**：每个素材入库时记下参考图身份——`pixiv:文件名` /
   `manga:系列|章|页` / `web:候选图 md5`。旧素材从 params.json 反查回填；
   其中一张被工作台「调」过、来源被覆盖的，用"裁剪框套候选图逐张比对"反查出了
   原始候选（差异 0.84 vs 次小 51，一目了然）。
2. **capture 的 fresh 参数**：用户说「再来一张/换一张/看看别的」→ 导演带
   `fresh=true`；app 层把同话题既有素材的 src_fp 收成 avoid 集合传给取材器。
   非 fresh 且库里命中 → 直接上屏，并在工具返回里提示"要新的传 fresh=true"。
3. **取材器去重**：pixiv 索引跳过用过的文件；漫画从候选页里挑没描过的、
   前两章没有就往后翻；网搜把用过的候选滤掉、存货不够就再下一批，全都用过才退回。
   于是"再来一张"每喊一次都能拿到不一样的参考图。
4. **选图标准加严**（vision.pick 提示词）：主体要完整、不被裁切、占画面一半以上，
   背景干净、少杂物；荧光棒海/人群/拼贴这类候选会被排除。实测同一句
   "初音未来 演唱会舞台"从"荧光棒照片"改选到"舞台插画"。

## 19. 舞台（stage）：让屏幕「实时画」，而不是「贴张图」（2026-10-11 深夜·续三）

原片里最勾人的是右侧那块屏**一直在动**——不是整图抖动，是信息在流动：打字机逐字写、
数字在滚、曲线一段段长出来、粒子在飘、素材从噪点里显影。素材信号（assets.Signal）
做不到这点：它本质是「一张字符画 + 摇曳」。所以新增一层 `core/stage.py`：

1. **零件库**（6 种，每个都是 `(t) → 当时的样子` 的纯函数）：
   typewriter 打字机 / counter 计数器 / chart 曲线 / progress 进度条 /
   particles 粒子（star·snow·ash·rain·firefly）/ emerge 素材显影。
   坐标一律 0~1 比例；没写坐标的零件自动从上往下排。
2. **质感**沿用素材信号那一套：格底 + 发光（模糊叠加）+ 扫描线 + 调色板染色 +
   开演淡入。stage 与 show 是同一块屏的两种用法，不打架。
3. **导演工具 `stage`**（`core/tools.py`）：参数 `title + parts[]`；coerce 校验
   白名单、夹取数值、零件最多 5 个；`world.apply("stage")` 写 `stage_plan/stage_t0`

## 23. model3d 零件与 AI 画师 MVP：让软件内的 AI 自己生产画面（2026-10-11 深夜·续七）

**model3d 零件**（`core/stage.py`）：把仓库里闲置的 3D 引擎（`runtime/tuikit/space.py`）接进舞台——
AI 不写几何，只递「体块清单 + 相机关键帧」：

- `solids`：盒子（lo/hi、gable/pyramid 屋顶、spire 尖塔、lv 线亮）与折线（poly），≤40 个；
  自动地面网格；雾默认随相机距离自适应（near≈0.7×dist、far≈2.2×dist、floor 0.14）。
- `camera`：2~8 个轨道相机关键帧（t/yaw/pitch/dist/fov/target）自动补间，不写就按 bbox 自动取景。
- 渲染落点：`space.View(...).draw(st.layer)` 绝对坐标直绘；有 3D 零件时不画 2D 网格底
  （`Stage.has3d`）；`_span` 认相机末帧时间，busy 拉通。
- 工具表（`core/tools.py`）同步 schema 与清洗（solids/camera/grid/fog），兼容模型惯用的 `type` 别名。

**AI 画师闭环**（`core/painter.py`）：解放「软件内 AI 生产力」的第一块：

- `compose(brief)`：flash 写分镜单 JSON → coerce 校验（失败回传错误重试）→ 渲染实况截图 →
  视觉模型评审（严格格式：第 1 行「达标/不达标」+ ≤3 条修改建议）→ 带批评迭代（≤3 轮）→
  存 `assets/recipes/<slug>.json + .png`（含 brief/评审/轮数）。
- 防翻车：JSON 截断识别与压缩重试（max_tokens 8000）、评审超时不阻塞、kind 别名兼容。
- 挂接：导演新增 `compose` 工具（`core/director.py`）→ `Session._compose/_compose_worker`
  后台线程（仿 capture），画完 `world.apply("stage", plan)` 自动上屏 + 系统消息「画师交稿」。

试金石：直连导演「用立体线框画夜色霍格沃茨」→ 导演自己写 model3d 分镜直接上屏（21s）；
画师 CLI `python -m core.painter "雪夜中的长城…"` → 3 轮闭环存稿；网页端无头截图确认整幅渲染。
下一步（未做）：配方库接回复演入口、model3d 暖色/自发光体块、复杂动作零件。

## 24. 绘图能力升级：面明暗填充 / 亮窗 / 线型（2026-10-11 深夜·续八）

依据 `docs/TUI_GRAPHICS_SURVEY.md` 的调研，第一批「抄进来」的能力全部落在 `model3d` 上：

1. **面明暗填充**（`space.shade_tex/shade_box` + `View.solid(tex=...)` 钩子）：按面法线·光向
   做 lambert，把墙面填成密度渐变的字符——`shade_ramp='block'`（░▒▓█，默认，砖石感）或

3. **线型可选**（`line`）：`auto`（默认，横平竖直走 box 实线、斜线走点阵）/ `dots` / `box` / `bold`；
   auto 让轴对齐建筑轮廓从抖动点线变回硬朗实线。

默认全开（单盒/整场可写 `shade:false`、`windows:false` 关闭）；工具表与画师提示词同步。

## 25. 素材的语义动效：文字剪影（2026-10-12）

起点是 `docs/VIDEO_ANIMATION_STUDY.md` 的结论：原片里**没有「整图位移 / 缩放」这种动**
（动效全是局部的、语义的——字在打、数在跳、图在显影），而 `Signal` 现在的 sway / breathe /
push 恰恰是那一种。该换成局部的语义动效。这一轮先落地参考片里最有代表性的那条：
**文字剪影**（那条「文字鲸鱼」）。

- **地基早就埋好了**：`tools/trace.py` 描图时把「轮廓 + 特征字形」放进 `art`，内部格一律写成
  `':'`，注释就写着 *interior cell (fillable with a text stream)*，`draw_frame(..., stream=...)`
  也实现了填充——只是上屏的 `assets.Signal` 从没接这条线。
- **新动效 `text`**（`core/assets.py`）：剪影本身不晃（sway/head 归零），内部 `':'` 格改填一段
  流动的字，整片表面持续闪变；大片平色区（`plain=1`，脸等）留白不写。底压暗、字提亮，
  否则亮面上字色和底色撞在一起，字读不出来。
- **字流可控**：`show` / `capture` 新增 `text` 参数（`core/tools.py`），聊到什么就流什么；
  `World.signal_text` 记着它（`core/world.py`），`scene.render` 传给 `Signal`。
  中文别名：文字剪影 / 剪影 / 文字 / 文字流 / 流光 / 流字。
- **中文的取舍**：等宽字体没有中文字形，按内容换字体；中文在 5×10 的格子里根本写不下，
  隔一列填一个、字号提到 10——单字仍认不清，就当成「一整片会流动的字」来看，不追可读性。
- **性能**：逐格 `d.text` 是瓶颈（5086 格要 145ms）。改成**预算 L 蒙版 + `img.paste`**
  （实测像素一致，5086 次只要 8ms），整帧 208ms → 107ms（≈9fps，和 sway 的 49ms 同一量级）。
  顺手把「先铺底、再统一写字」拆成两遍：原先后一格的底会盖掉前一格溢出的字形。
- **预览**：`lab/signal_preview.py out.png 0 1 2 5 --asset <id> --motion text --text 霍格沃茨`。
- **和 stage 的 `silhouette` 的分工**：实聊时导演会把「让名字在屏上流动」派给 `stage` 的
  `silhouette` 零件（已有能力：用素材当蒙版、单色、塞在一个方框里）。`show ... motion=text`
  是另一条路——保住照片本身的形与色，只在内部填字。两条都留着，看场合选。

下一步（未做）：`Signal` 其余语义动效（分区形变，如发/衣襟/云）；粒子层（雪/灰/星/萤）与
文字层（台词字幕、计数、块光标）由对话内容驱动——即 STUDY 里那张「分层实时合成」表的其余几层。
